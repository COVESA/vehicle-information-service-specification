The Vehicle Information Service Specification (VISS) is a specification for access to vehicle information, including signals from sensors on control units within a vehicle's network, and services in the form of software applications that utilize vehicle signals for the service execution and are invoked by calling a procedure having input and output parameters. This information is exposed through a hierarchical, tree-like taxonomy as defined in the COVESA Hierarchical Information Model (HIM), and is provided in JSON format. A server implementing VISS may be hosted within the vehicle or on external platforms.

VISS enables a broad range of use cases, including predictive maintenance, usage-based insurance, fleet management, and real-time driver assistance services. In the context of artificial intelligence, VISS serves as a critical data access layer, providing high-quality, real-time vehicle data that can be utilized by AI algorithms for tasks such as anomaly detection, driver behavior analysis, energy optimization, and contextual decision-making.

The first version of VISS, which has been implemented and deployed in production vehicles, supported only WebSocket as a transport protocol.
The version 2.0 is generalized to work across also the HTTP and MQTT transport protocols to improve the support for different use cases. It also contains improved subscription capabilities and added an access control mechanism.
The version 3.0 included the gRPC transport protocol but also simplified addition of other transport protocols by placing the normative requirement on the message payload only, and not also on what transport protocol to use. Several new features were added such as file transfer, payload encoding, and improved server capabilities representation.
The version 3.1 replaced the VSS rule set for how to define the content of a tree with the HIM data profile rule set and included support for the Unix domain socket transport protocol.
This specification, version 3.2, extends the usage of the HIM data model to also include the HIM service profile.

There are four parts to this specification, [[CORE]], [[TRANSPORT]], [[PAYLOAD ENCODING]], and SERVICES. This document, the VISS version 3.2 SERVICES specification, describes the service related parts of the interface. The companion specifications [[CORE]] describes the messaging layer, [[TRANSPORT]] describes the deviations form the CORE specification that are used by some transport protocols, and [[PAYLOAD ENCODING]] describes payload encodings that are used in some cases.

Introduction

This specification describes the service related parts of the VISS interface. Services are typically realized as software components that are deployed as shown in the figure below.

The service is the logical end point of the client request, the service implementation then uses signals in the vehicle signal domain to execute the service. The signal access can either be directly to the native signals or it can use the VISS signal abstraction, the latter may enable the service to be interoperable on different vehicle models and brands.
The VISS Service profile follows the model from VISS Vehicledata profile in that the data describing the service signature (procedure name, input, output) is handled as data in the interface. Any changes to the service signature will thus not require any changes of the interface. This is true for all changes all the way to a complete switch to another service domain tree.

Terminology

The acronym 'VISSv3.2' is used to refer to this document, the VISS version 3.2 specification.
The acronym 'HIM' is used to refer to the 'Hierarchical Information Model' which is hosted by COVESA.
The acronym 'VSS' is used to refer to the 'Vehicle Signal Specification' which is hosted by COVESA.
The term 'WebSocket' when used in this specification, is as defined in the W3C WebSocket API and [[RFC6455]], the WebSocket Protocol.

Service Overview

A service is in this specification defined as a software application that utilize vehicle signals for the service execution and a client invokes it by calling a procedure having input and output parameters. A service is defined by a service signature as shown below. 


        ProcedureName(input1: datatype1, ..., inputN: datatypeN): (outputA: datatypeA, ..., outputM: datatypeM)
where ProcedureName is the name of the procedure, inputX is the X:th input parameter, datatypeX is the datatype of the X:th input parameter, outputY is the Y:th output parameter, datatypeY is the datatype of the Y:th output parameter.
The procedure shall have zero or more input parameters and one or more output parameters.
The signature components are mapped to nodes in a HIM service tree as shown below.
  • ProcedureName: The procedure name is mapped to a node with the name ProcedureName and the node type 'procedure'.
  • inputX: An input parameter is mapped to a node with the name InputX and the node type 'property' or 'symlink'. This node must be a child to a node with the name Input and the node type 'iostruct', which in its turn must be a child to the node with the name ProcedureName.
  • outputY: An output parameter is mapped to a node with the name OutputY and the node type 'property' or 'symlink'. This node must be a child to a node with the name Output and the node type 'iostruct', which in its turn must be a child to the node with the name ProcedureName.
For more information about service node types, see the Service Data Model chapter.
The tree structure defining a service depends on whether the service manages one or multiple resources, see the HIM specification HIM: Single resource and HIM: Multiple resources.

Service Data Model

The service data model is defined by the HIM service profile.

Status

The status of a service is a stateful parameter and shall be preserved by the server. It must be one of the following states:

  • UNKNOWN: The status of the service is unknown.
  • ONGOING: The service has been invoked but has not yet reached a successful termination, or terminated due to being canceled or ending in failure.
  • SUCCESSFUL: The service is not ONGOING and the latest invocation of the service terminated successfully.
  • CANCELED: The service is not ONGOING and the latest invocation of the service terminated due to being canceled.
  • FAILED: The service is not ONGOING and the latest invocation of the service terminated due to a failure.
The Status string datatype is restricted to the allowed values from the list above. The Status parameter shall be included in all response and event messages, set to the current value. A server shall at startup have access to the last known Status of the services it manages, typically from the previous ignition cycle. In case this is not possible then it shall be set to UNKNOWN. Input and output data in response or event messages are undefined if the status is set to UNKNOWN or FAILED. A service may be set to a maximum allowed execution time which when exceeded leads to the server terminating it, see HIM Procedure Node.

Action

The Action parameter shall be included in all request, response and event messages. For transport protocols with methods that do not define a payload the 'action' parameter shall be omitted.
The different requests shall use the action values shown in the table below. The same action value shall be used in the response message.
  • Invoke: "action": "invoke"
  • Monitor: "action": "monitor"
  • Cancel: "action": "cancel"
  • Service Discovery: "action": "discover"
Event messages shall have the following action value:
  • Event: "action": "monitoring"

Service Data

The VISS signal profile defines a "data" object for the JSON representation of the output signal(s). This data represents the current value of the signal(s) together with capture time stamp(s).
The VISS service profile data model has separate definitions for input and output data which then each are correspondingly defined below.

Input Data

The definition of the service input data is shown below. 
                  "indata": {"input": {input-params}, "ts": "ddtt"}
where "input-params" is the JSON representation of the service input parameters with their corresponding values and "ddtt" is the timestamp value associated with the server reception of the input parameters.

Output Data

Output Data Single Resource

The definition of the service output data is shown below for services that manage a single resource. 
                    "outdata": {"output": {output-params}, "ts": "ddtt"}
where "output-params" is the JSON representation of the service output parameters with their corresponding values and "ddtt" is the timestamp value associated with the capture of the output parameters.

Output Data Multiple Resources

The definition of the service output data is shown below for services that manage multiple resources. 
                    "outdata": [{"path-snippet1":{"output": {output-params}, "ts": "ddtt"}}, {"path-snippetN":{"output": {output-params}, "ts": "ddtt"}}]
where "path-snippetX" are the path snippets that were declared by the filter expression in the request, and "output-params" and "ddtt" represent the same semantics as in the single resource case.
The "path-snippetX" expressions must not contain wildcards.

Exceptions

  • For HTTP the POST method is used for all request actions except for Service discovery that uses the GET method.
  • The Invoke and Monitor requests will if sent over HTTP only return the response message. If the Status in the response is set to ONGOING then the client is recommended to issue a Monitor request to the same service over a transport protocol that supports event messages, e. g. WebSocket or MQTT.

Service Interface

The service interface builds on the syntax and concepts used in the CORE:Data Interface for access to vehicle signals. The differences are listed below.

  • The service interface must only be used on trees that have a 'domain' metadata value with a right-most segment named 'Service", defined in the HIM configuration file.
  • The available methods are: invoke / monitor / cancel / discover.
  • A request can only invoke one service.
  • All response, event and error messages shall include a Status parameter.
  • The requests defined in the service interface shall only be issued using paths addressing nodes of node type 'procedure', except for service discovery requests that may use a path addressing nodes of type 'branch'.
  • The available filter variants are: timebased / status / all / none.
  • If an invoke or monitor request leads to that an event session is started then it is automatically terminated when the service is successfully terminated, or terminated due to being cancelled or ending in failure. The server must then issue an event or error message with the Status set appropriately.
  • The client that invoked a service and have access to the serviceId of the ONGOING service may terminate the service at any point by calling Cancel.
  • An Invoke request to a service that has the Status ONGOING shall be rejected with a response error message set to 503/service_unavailable.
  • A client monitoring an ONGOING service without having invoked it cannot terminate the service by calling Cancel, but the Cancel call will terminate its monitoring session.
  • A monitor request returns the latest input values that have been used to invoke the service in the response. If the response Status has the value ONGOING then events will be issued until the Status value is changed to either SUCCESSFUL, CANCELED or FAILED.

Service Methods

A client can apply the following types of operations on a service:

  • Invoke: A request to execute a service.
  • Monitor: A request to get monitoring data of a service.
  • Cancel: A request to cancel the session started by a previous invoke or monitor request.
  • Discovery: A request to get metadata describing one or more services.
The service signature is declared in the tree following the HIM Service profile syntax, a client request must conform to the service signature. A service shall have zero or more input parameters, and one or more output parameters. If the request does not conform to the signature the server shall reply with an error message and shall not begin execution of the service. The server must also issue an error message if it during the service execution enters into a failure state.
The time duration that a service require for its execution may be neglible in terms of the total time between that the request was issued and that a response was received. In such cases the service is not expected to issue any asynchronous event messages to report its execution progress. Services that have a non-negligible time duration shall issue event messages to report its execution progress. The rate of event messages is an implementation decision, but the service must as a minimum issue an event at the successful termination of the execution, or if it enters into a failure state.
To realize these operations the methods described in the following chapters are available.

Invoke

Purpose: Invoke a service addressed by the given path. Depending on filter variant selection and service duration a monitoring session may be initiated.
The Invoke request will return a synchronous response. If its execution duration is non-negligible and the filter variant is not set to "none" then the service will issue one or more event messages. If a serviceId is returned to the client then it must be unique and it must not be reused in responses to other clients. A client that has invoked a service to receive event messages cannot stop receiving the event messages without also stopping the service execution through a Cancel request.
Request arguments, of which path and filter are mandatory and input is mandatory in case the service signature specifies it:

  • path: The path to a node with the node type procedure.
  • input: The input parameters as specified by the service signature.
  • filter: Additional parameters configuring the type of monitoring.
  • authorization: The authorization token.

Success response arguments of which path, status and timestamp are mandatory, serviceId is mandatory if a session is started, else it shall be omitted. Outdata is mandatory in case the service signature specifies it. The outdata in the sync response of an Invoke request shall contain the current values of the output parameters at the time the service execution begins, before any change from the service execution has occurred.

  • path: The path to the service.
  • outdata: The service output parameters as specified in the service signature.
  • status: The execution Status.
  • serviceId: A reference Id for the monitoring session
  • timestamp: The start time of the server execution. For services with a neglible execution duration this also represent the time of termination.
Event message arguments of which path, status, serviceId and timestamp are mandatory and outdata is mandatory in case the service signature specifies it.
  • path: The path to the service.
  • outdata: The service output parameters as specified in the service signature.
  • status: The execution Status.
  • serviceId: A reference Id for the monitoring session.
  • timestamp: The issuance time of the event. If Status is not ONGOING then this also represents the time of termination.

Monitor

Purpose: Initiate a monitoring session of a service.
If the service execution is ongoing and the filter variant is not set to "none"then a monitoring session is initiated, else only the synchronous response will be issued. If a serviceId is returned to the client then it must be unique and it must not be reused in responses to other clients.
Request arguments, of which path and filter are mandatory:

  • path: The path to a node with the node type procedure.
  • filter: Additional parameters configuring the type of monitoring.
  • authorization: The authorization token.

Success response arguments of which path, status, and timestamp are mandatory. serviceId is mandatory if the service execution duration is non-negligible, else it shall not be present. Indata and outdata are mandatory in case the service signature specifies it:

  • path: The path to the service.
  • indata: The input parameters as specified by the service signature. The input parameters contain the values from the latest invocation of the service. If the Status is not ONGOING then the indata represents a historical context.
  • outdata: The service output parameters as specified in the service signature.
  • status: The execution Status.
  • serviceId: A reference Id for the monitoring session.
  • timestamp: The time stamp represent the time at which the status and output values were captured.
Event message arguments of which path, status, serviceId and timestamp are mandatory and outdata is mandatory in case the service signature specifies it.
  • path: The path to the service.
  • outdata: The service output parameters as specified in the service signature.
  • status: The execution Status.
  • serviceId: A reference Id for the monitoring session.
  • timestamp: The issuance time of the event. If Status is not ONGOING then this also represents the time of termination.

Cancel

Purpose: Cancels either an ongoing service or a monitoring session.
Cancels an ongoing service if the service Id was obtained in the response of an Invoke request. If it was obtained in the response of a Monitor request then that monitoring session is cancelled but the service execution is unaffected.
Request arguments, of which serviceId is mandatory:

  • serviceId: The Id of an ongoing session.

Success response arguments of which status, serviceId and timestamp are mandatory. Outdata is mandatory in case the service signature specifies it:

  • status: The execution Status.
  • outdata: The service output parameters as specified in the service signature.
  • serviceId: The Id of the canceled session.
  • timestamp: The time stamp represent the time at which the session was cancelled.
If the serviceId in a Cancel request does not correspond to any active session the server shall respond with error number 404, reason unavailable_data.

Service Discovery

Purpose: Retrieve metadata describing one or more services.
The metadata describes a service and declares its signature.
Request arguments, of which path is mandatory:

  • path: The path to a node with the node type branch or procedure.
  • filter: A filter defining the addressed resources.
  • authorization: The authorization token.
The path must either address a procedure node or a branch node that is not a descendant node to a procedure node.
A filter must only be of the variant "resource" and must not be used if the path addresses a branch node.

Success response arguments of which metadata and timestamp are mandatory:

  • metadata: A JSON representation of the content of the addressed subtree.
  • timestamp: The time stamp represent the time at which the response was submitted.

Service Filter

The service filter is used to configure the event message triggering during the service monitoring session. The rate at which a service updates its output parameters is implementation specific and it is typically different for different services. The service implementation shall update its Status parameter directly when the state of the service changes. The filter settings do not affect this "native" rate of the service implementation, it can only reduce the rate of events being issued to the client. If the filter setting requests a higher rate than the native rate it will get events at the native rate. Services that do not issue any events will ignore the filter and act as if the variant is set to "none". Information on what is the native rate may be available in the procedure metadata, see HIM Procedure Node.
The syntax follows the Data profile filter syntax with variant and parameter keys as shown below. 


            "filter": {"variant": "name", "parameter": {"param-name": "param-value"}}
There is one difference in that the "parameter" key-value pair is optional as it is not used in some variants.
The supported variants are defined in the following.

Filter Variant Timebased

This filter variant issues events with a fixed time period between the events. The syntax is shown below. 


              "filter": {"variant": "timebased", "parameter": {"period": "param-value"}}
where "param-value" is an integer and represents the period time in milliseconds. Events will also be issued if the Status parameter changes.

Filter Variant Status

This filter variant issues events when the Status parameter changes. The syntax is shown below. 


              "filter": {"variant": "status"}
The "parameter" key-value pair shall not be present.

Filter Variant All

This filter variant issues an event when either the Status parameter changes, or any output parameter changes. If more than one output parameter change before the server have issued an event the server may include both changes in the same event. The syntax is shown below. 


              "filter": {"variant": "all"}
The "parameter" key-value pair shall not be present.

Filter Variant None

This filter variant do not issue any events. The syntax is shown below. 


              "filter": {"variant": "none"}
The "parameter" key-value pair shall not be present.

Filter Variant Resource

This filter variant selects the resource(s) that a request shall address when the service manages multiple resources. The syntax is shown below. 


              "filter": {"variant": "resource", "parameter": ["Row1.*"]}
The "parameter" value shall be an array containing one or more path snippet(s) that is to be inserted in the full path that points to the respective service Input and Output nodes of the addressed resources. A path segment name in a snippet may be replaced by the wildcard operator "*".
If a rsource variant filter is not included in a request addressing a service that is manages multiple resources then the response and any event messages will contain output data from all the resources.

Multiple Filters

The Resource variant filter can be combined with any one of the other filter variants. These other filter variants are only allowed to be combined with the Resource filter variant. An array expression shall be used to create a combined filter expression as shown in the example below. 


              "filter": [{"variant": "status"}, {"variant": "resource", "parameter": ["Row1.DriverSide", "Row2.PassengerSide"]}]

A service error message shall contain error information as defined in CORE:Error Information and the service Status parameter, see the error message example.
